WDAC for Beginners

Windows Defender Application Control (now branded App Control for Business) explained step by step, with hands-on PowerShell examples for Windows Server 2025 Core.

1. What is WDAC?

WDAC is a Windows security feature that decides which code is allowed to run on a machine. Anything not explicitly trusted by your policy is blocked: executables, DLLs, drivers, scripts and installers.

Name check: Microsoft renamed WDAC to App Control for Business. The cmdlets, file formats and many docs still say WDAC, CI (Code Integrity) or ConfigCI. They are all the same technology.

Why use it?

  • Stops malware and ransomware that runs from Downloads, Temp or an attacker's dropped files, because unknown code is simply not allowed.
  • Allow-list model: "deny by default, allow what I trust" is far stronger than "detect bad stuff".
  • Kernel-level enforcement: it applies to drivers and to admin users too, so an admin cannot casually bypass it.
  • Compliance: a common requirement in hardened server baselines.

Mental model

Think of a nightclub guest list. Antivirus is a bouncer who knows a list of troublemakers. WDAC is a bouncer who only lets in people on the guest list, whoever they are.

Where it works

Windows 10/11 and Windows Server 2016 and later, including Server Core. Windows Server 2025 supports the modern multiple-policy format (base + supplemental policies).

2. Architecture of WDAC

WDAC is enforced by Code Integrity (CI), a component of the Windows kernel. Every time something tries to load, CI checks it against the active policies.

Policy authoring (XML)Written with PowerShell (ConfigCI module), the App Control Wizard, or templates in C:\Windows\schemas\CodeIntegrity\ExamplePolicies
▼ ConvertFrom-CIPolicy
Binary policy (.cip)Compiled file named {PolicyGUID}.cip
▼ deploy (CiTool, Group Policy, Intune, MDM, file copy)
Active policy storeC:\Windows\System32\CodeIntegrity\CiPolicies\Active\ (also stored in the EFI partition so it applies at early boot)
▼ loaded by
KMCIKernel Mode Code Integrity. Checks drivers and kernel code.
UMCIUser Mode Code Integrity. Checks EXE, DLL, scripts, MSI, packaged apps.
▼ decision
AllowCode runs.
Audit modeCode runs, event is logged.
Enforce modeCode is blocked, event is logged.
▼
Event logApplications and Services Logs → Microsoft → Windows → CodeIntegrity → Operational

How a file is evaluated (simplified)

  1. A process tries to start, or a DLL/driver tries to load.
  2. Code Integrity looks at the file's digital signature, hash, file attributes or path.
  3. It compares them with the rules in every active policy. An explicit Deny always wins over Allow.
  4. No matching Allow rule means the file is blocked (enforce) or logged (audit).

Extra trust sources (optional)

  • Managed Installer: trust anything installed by a designated tool such as Configuration Manager.
  • Intelligent Security Graph (ISG): trust files Microsoft's cloud reputation considers safe.
When a policy enforces user mode, PowerShell automatically switches to Constrained Language Mode for scripts that are not trusted by the policy. This is an expected side effect and part of the protection.

3. Policy components and types

3.1 Policy types

TypeWhat it isTypical use
Base policyStand-alone policy with its own GUID. Defines the core trust.Your main allow-list for a server role.
Supplemental policyExtends one base policy by adding more allow rules. It cannot remove or change base rules. The base needs rule option 17.Per-team or per-app additions without editing the base.
Multiple base policiesSeveral base policies active at once. A file must be allowed by all of them (intersection).Layering a baseline plus a deny-list.
Audit mode policyRule option 3 set. Nothing is blocked, only logged.Testing before enforcement.
Enforced policyRule option 3 removed. Unauthorized code is blocked.Production.
Signed policyPolicy signed with your certificate. Cannot be removed or changed without a matching signature.High-security, tamper-resistant environments. Advanced topic.

SigningScenariosValue 131 = kernel mode, value 12 = user mode. Allow/deny entries are grouped here.

3.4 File rule levels (how a file is identified)

From most flexible to most specific:

LevelTrustsComment
RootCertificateAnything chained to a root CAVery broad, rarely recommended.
PcaCertificateAnything from an issuing CABroad, commonly the best "everything from vendor X" level for Microsoft.
PublisherPCA + the publisher (leaf subject name)"Everything signed by Contoso Ltd".
FilePublisherPublisher + file name + minimum versionGood balance. Recommended default.
SignedVersionPublisher + minimum versionAny file from the publisher at or above a version.

Rule of thumb: prefer FilePublisher with -Fallback Hash. The fallback covers unsigned files automatically.

4. Install / configure on Windows Server 2025 Core

WDAC is built into Windows. There is no role or feature to install. What you need on Server Core is access to PowerShell, the ConfigCI module and a way to move files around.

  1. Get a shell. After logging in to Server Core you land in cmd. Start PowerShell: 
    powershell
    Or work remotely from your admin PC (recommended, since you can copy/paste): 
    Enable-PSRemoting -Force                    # on the server
Enter-PSSession -ComputerName CORE01 -Credential (Get-Credential)   # from your admin PC
  2. Check the OS and the module. 
    Get-ComputerInfo | Select-Object OsName, OsVersion, WindowsEditionId
Get-Command -Module ConfigCI | Select-Object Name
Test-Path C:\Windows\System32\CiTool.exe
    You should see New-CIPolicy, ConvertFrom-CIPolicy, Set-RuleOption, Merge-CIPolicy and others.
  3. Check the built-in templates. 
    Get-ChildItem C:\Windows\schemas\CodeIntegrity\ExamplePolicies
    Useful ones: AllowMicrosoft.xml, DefaultWindows_Audit.xml, DefaultWindows_Enforced.xml, AllowAll.xml, DenyAllAudit.xml.
  4. Create working folders. 
    New-Item -ItemType Directory -Force C:\WDAC\Policies, C:\WDAC\Binary | Out-Null
  5. Know your deployment methods.
    MethodWhen
    CiTool.exe --update-policy file.cipLocal, lab, and Server 2025. Applies without reboot.
    Copy file to ...\CiPolicies\Active\ and rebootFallback if CiTool is not available.
    Group Policy (Deploy Windows Defender Application Control)Domain environments. Points to a policy file path.
    Intune / MDM / Configuration ManagerManaged fleets.
  6. Safety net before you start. Take a VM checkpoint/snapshot. A badly built enforced policy can stop the server booting normally.
Always begin in audit mode. Never enforce a policy you have not tested on a lab VM first.
Server Core has Notepad, so notepad file.xml still opens a window for quick edits. The graphical App Control Wizard cannot run on Core; use it on your admin PC and copy the resulting XML over.

5. Step-by-step: create and configure your first policy

Goal: a policy that allows Windows, Microsoft-signed code and your own approved software, starts in audit mode, and is then moved to enforce mode.

  1. Start from a template. 
    Copy-Item C:\Windows\schemas\CodeIntegrity\ExamplePolicies\DefaultWindows_Audit.xml C:\WDAC\Policies\MyBase.xml
    DefaultWindows allows Windows components and the Store apps. For a server you may prefer AllowMicrosoft.xml which also trusts all Microsoft-signed software.
  2. Name the policy and give it an ID. 
    Set-CIPolicyIdInfo -FilePath C:\WDAC\Policies\MyBase.xml -PolicyName "Lab Base Policy" -ResetPolicyID
    -ResetPolicyID generates a new GUID, so you do not clash with another policy.
  3. Set the rule options. Allow supplementals and make sure it is in audit mode: 
    $p = "C:\WDAC\Policies\MyBase.xml"
Set-RuleOption -FilePath $p -Option 3                 # Audit mode ON
Set-RuleOption -FilePath $p -Option 17                # Allow supplemental policies
Set-RuleOption -FilePath $p -Option 16                # Update without reboot
Set-RuleOption -FilePath $p -Option 0                 # Enforce user mode too
  4. Compile to binary. For the multiple-policy format the file must be named after the PolicyID: 
    $id = ([xml](Get-Content $p)).SiPolicy.PolicyID
ConvertFrom-CIPolicy -XmlFilePath $p -BinaryFilePath "C:\WDAC\Binary\$id.cip"
$id
  5. Deploy it. 
    CiTool.exe --update-policy "C:\WDAC\Binary\$id.cip"
CiTool.exe --list-policies
    You should see your policy listed. In older builds without CiTool, copy the file to C:\Windows\System32\CodeIntegrity\CiPolicies\Active\ and reboot.
  6. Run your workloads (audit period). Use the server normally for several days: start services, run backups, patch, install roles, run scheduled tasks. Then read the log: 
    Get-WinEvent -LogName "Microsoft-Windows-CodeIntegrity/Operational" |
  Where-Object Id -in 3076,3077 |
  Select-Object TimeCreated, Id, Message -First 10 | Format-List
    3076 = would have been blocked (audit). 3077 = was blocked (enforced).
  7. Generate rules from the audit events. This turns what was "blocked" into allow rules you can review: 
    New-CIPolicy -FilePath C:\WDAC\Policies\FromAudit.xml -Audit -Level FilePublisher -Fallback Hash -UserPEs -MultiplePolicyFormat
    Open FromAudit.xml and remove anything you do not trust. Do not blindly approve everything that appeared in the log.
  8. Merge the approved rules into the base. 
    Merge-CIPolicy -PolicyPaths $p, C:\WDAC\Policies\FromAudit.xml -OutputFilePath $p
  9. Switch to enforce mode (delete option 3), recompile and redeploy: 
    Set-RuleOption -FilePath $p -Option 3 -Delete
ConvertFrom-CIPolicy -XmlFilePath $p -BinaryFilePath "C:\WDAC\Binary\$id.cip"
CiTool.exe --update-policy "C:\WDAC\Binary\$id.cip"
  10. Test enforcement. Copy an unsigned or unapproved program (for example a downloaded tool) to C:\Temp and try to run it. It should fail with "This program is blocked by group policy", and event 3077 appears.
Rollback: CiTool.exe --remove-policy {GUID} then reboot if needed. Keep your console/VM access open until you have verified the server still works.

5b. Basic commands you will use every day

Keep this section open while you work. Commands are grouped by task. $w is a working folder, {GUID} is a policy ID.

Check the system

$PSVersionTable.PSVersion                                   # PowerShell version
Get-ComputerInfo | Select-Object OsName, OsVersion           # OS and build
Get-Command -Module ConfigCI                                 # list policy cmdlets
Get-Help New-CIPolicy -Examples                              # built-in examples for any cmdlet
Get-Command CiTool.exe                                       # is CiTool present?

List and inspect deployed policies

CiTool.exe --list-policies                                   # all policies (short: CiTool -lp)
CiTool.exe --list-policies -json                             # same, as JSON
Get-ChildItem C:\Windows\System32\CodeIntegrity\CiPolicies\Active   # the .cip files themselves

# Enforcement status: 0 = off, 1 = audit, 2 = enforced
Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard |
  Select-Object CodeIntegrityPolicyEnforcementStatus, UsermodeCodeIntegrityPolicyEnforcementStatus

Read a policy XML

$x = [xml](Get-Content C:\WDAC\Policies\MyBase.xml)
$x.SiPolicy.PolicyID                       # this policy's GUID
$x.SiPolicy.BasePolicyID                   # base GUID (same as PolicyID for a base policy)
$x.SiPolicy.PolicyType                     # Base Policy or Supplemental Policy
$x.SiPolicy.VersionEx                      # version number
$x.SiPolicy.Rules.Rule.Option              # all rule options set

Create, edit and compile

New-CIPolicy -FilePath out.xml -ScanPath C:\Apps -Level FilePublisher -Fallback Hash -UserPEs -MultiplePolicyFormat
Set-CIPolicyIdInfo -FilePath out.xml -PolicyName "My Policy" -ResetPolicyID
Set-RuleOption -FilePath out.xml -Option 3                   # add option 3 (audit)
Set-RuleOption -FilePath out.xml -Option 3 -Delete           # remove option 3 (enforce)
Set-CIPolicyVersion -FilePath out.xml -Version "1.0.0.5"     # bump version
Merge-CIPolicy -PolicyPaths a.xml,b.xml -OutputFilePath merged.xml
ConvertFrom-CIPolicy -XmlFilePath out.xml -BinaryFilePath "C:\WDAC\Binary\{GUID}.cip"

Deploy, refresh and remove

CiTool.exe --update-policy "C:\WDAC\Binary\{GUID}.cip"       # add or replace
CiTool.exe --refresh                                         # reload all policies now
CiTool.exe --remove-policy "{GUID}"                          # remove one policy
Restart-Computer                                             # only when a policy needs it

Watch the logs

# Last 10 audit or block events
Get-WinEvent -LogName Microsoft-Windows-CodeIntegrity/Operational -MaxEvents 200 |
  Where-Object Id -in 3076,3077 | Select-Object -First 10 TimeCreated, Id, Message | Format-List

# Count events by type
Get-WinEvent -LogName Microsoft-Windows-CodeIntegrity/Operational |
  Group-Object Id | Sort-Object Count -Descending | Select-Object Count, Name

# Confirm a policy was loaded
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-CodeIntegrity/Operational'; Id=3099} -MaxEvents 5

Back up and restore

New-Item -ItemType Directory C:\WDAC\Backup -Force | Out-Null
Copy-Item C:\Windows\System32\CodeIntegrity\CiPolicies\Active\*.cip C:\WDAC\Backup\                  # backup
Copy-Item C:\WDAC\Backup\{GUID}.cip C:\Windows\System32\CodeIntegrity\CiPolicies\Active\ -Force; CiTool.exe --refresh   # restore

Event IDs to remember

IDMeaning
3099A policy was loaded
3076Would have been blocked (audit mode)
3077Was blocked (enforced)
3089Signature details for the file in the neighbouring 3076/3077 event

6. AppLocker vs WDAC

Both are application control technologies. They can be used together, but WDAC is Microsoft's strategic choice for strong security.

TopicAppLockerWDAC (App Control)
Security boundaryNot a defined security boundary (user-mode feature; can be bypassed by admins or exploits)Serviced as a security feature; enforced in the kernel
ScopeUser mode only (EXE, DLL, scripts, MSI, packaged apps)Kernel mode (drivers) and user mode
Applies toPer user or group (SID based)Whole device, all users
Rule modelAllow rules with exceptions; deny possibleAllow and Deny, signers, hash, path, attributes
Rule creationGUI (Local Security Policy), PowerShellPowerShell, App Control Wizard, XML
Audit modeYesYes
Multiple policiesOne effective policy setMultiple base + supplemental policies
Managed installer / ISGNoYes
Script controlRules for scriptsEnforced via PowerShell Constrained Language Mode and script hosts
Windows editionsEnterprise/Education (rule enforcement), ServerAll editions can enforce; authoring tools in all
Event logMicrosoft-Windows-AppLocker/* (8003, 8004...)Microsoft-Windows-CodeIntegrity/Operational (3076, 3077...)
Best forPer-user restrictions on a shared machine; legacy setupsServers, kiosks, high-security endpoints
Practical guidance: use WDAC as your device-wide baseline. Keep AppLocker only if you need per-user rules on top (for example, different rules for admins and standard users on a terminal server). If both exist, a file must satisfy both.

7. Seventeen simple examples

All examples assume the working folders from section 4 and use PowerShell on Server Core. Replace the sample paths with your own. Each example follows the same pattern: define → build → deploy → test.

Reusable helper: paste this once per session. It compiles an XML policy and deploys it. 
function Deploy-Wdac($Xml){
  $id = ([xml](Get-Content $Xml)).SiPolicy.PolicyID
  $cip = "C:\WDAC\Binary\$id.cip"
  ConvertFrom-CIPolicy -XmlFilePath $Xml -BinaryFilePath $cip
  CiTool.exe --update-policy $cip
}

Example 1: Audit-only policy (see what would be blocked) Audit

Define: learn what runs on the server without breaking anything.

$x = "C:\WDAC\Policies\Ex1.xml"
Copy-Item C:\Windows\schemas\CodeIntegrity\ExamplePolicies\DefaultWindows_Audit.xml $x
Set-CIPolicyIdInfo $x -PolicyName "Ex1 Audit" -ResetPolicyID
Deploy-Wdac $x

Test: run any unsigned tool. It starts normally. Then run:

Get-WinEvent -LogName Microsoft-Windows-CodeIntegrity/Operational -MaxEvents 5 | Where Id -eq 3076 | Format-List TimeCreated,Message

Example 2: Allow only Windows and Microsoft-signed software Enforce

Define: the classic "Microsoft only" server. Everything else is blocked.

$x = "C:\WDAC\Policies\Ex2.xml"
Copy-Item C:\Windows\schemas\CodeIntegrity\ExamplePolicies\AllowMicrosoft.xml $x
Set-CIPolicyIdInfo $x -PolicyName "Ex2 Microsoft Only" -ResetPolicyID
Set-RuleOption $x -Option 3 -Delete       # make sure audit is OFF
Deploy-Wdac $x

Test: copy any third-party unsigned .exe to C:\Temp and run it: blocked. notepad.exe, whoami.exe still run.

Run this on a VM with a checkpoint first.

Example 3: Allow one vendor by publisher Allow

Define: trust everything signed by a vendor (say, an app installed in C:\Program Files\Contoso).

$base = "C:\WDAC\Policies\Ex2.xml"
$drivers = Get-SystemDriver -ScanPath "C:\Program Files\Contoso" -UserPEs
$rule = New-CIPolicyRule -DriverFiles $drivers -Level Publisher
Merge-CIPolicy -PolicyPaths $base -OutputFilePath C:\WDAC\Policies\Ex3.xml -Rules $rule
Set-CIPolicyIdInfo C:\WDAC\Policies\Ex3.xml -PolicyName "Ex3 Contoso Publisher" -ResetPolicyID
Deploy-Wdac C:\WDAC\Policies\Ex3.xml

Test: the Contoso app starts. An unsigned tool is still blocked. Note: the app must be signed; unsigned files fall back to nothing at the Publisher level (see Example 6).

Example 4: Block a specific tool by file name (Deny rule) Deny

Define: block mshta.exe (a commonly abused scripting host), even though Microsoft signs it.

$deny = New-CIPolicyRule -DriverFilePath C:\Windows\System32\mshta.exe -Level FileName -SpecificFileNameLevel OriginalFileName -Deny
Merge-CIPolicy -PolicyPaths C:\WDAC\Policies\Ex2.xml -OutputFilePath C:\WDAC\Policies\Ex4.xml -Rules $deny
Set-CIPolicyIdInfo C:\WDAC\Policies\Ex4.xml -PolicyName "Ex4 Block mshta" -ResetPolicyID
Deploy-Wdac C:\WDAC\Policies\Ex4.xml

Test: mshta.exe about:blank now fails; renaming the file does not help because the original file name is used.

Microsoft publishes a recommended block-rules list for known bypass binaries. Review it when you harden a real server.

Example 5: Block one exact file by hash Deny

Define: forbid one known-bad or unwanted file regardless of name or location.

$deny = New-CIPolicyRule -DriverFilePath C:\Temp\unwanted.exe -Level Hash -Deny
Merge-CIPolicy -PolicyPaths C:\WDAC\Policies\Ex2.xml -OutputFilePath C:\WDAC\Policies\Ex5.xml -Rules $deny
Set-CIPolicyIdInfo C:\WDAC\Policies\Ex5.xml -PolicyName "Ex5 Hash Deny" -ResetPolicyID
Deploy-Wdac C:\WDAC\Policies\Ex5.xml

Test: rename and move unwanted.exe; it is still blocked because the hash is identical. Change a single byte and it will run (hashes are exact), which is why hash rules suit single known files only.

Example 6: Allow an unsigned in-house app by hash Allow

Define: your own script host or tool has no digital signature.

$allow = New-CIPolicyRule -DriverFilePath C:\Apps\inventory.exe -Level Hash
Merge-CIPolicy -PolicyPaths C:\WDAC\Policies\Ex2.xml -OutputFilePath C:\WDAC\Policies\Ex6.xml -Rules $allow
Set-CIPolicyIdInfo C:\WDAC\Policies\Ex6.xml -PolicyName "Ex6 InHouse Hash" -ResetPolicyID
Deploy-Wdac C:\WDAC\Policies\Ex6.xml

Test: inventory.exe runs. After you rebuild the app the hash changes and it is blocked until you update the policy. Signing the app with your own code-signing certificate avoids this.

Example 7: Allow an admin-only folder by path Allow

Define: trust everything in C:\ApprovedTools.

New-Item -ItemType Directory C:\ApprovedTools -Force | Out-Null
$rule = New-CIPolicyRule -FilePathRule "C:\ApprovedTools\*"
Merge-CIPolicy -PolicyPaths C:\WDAC\Policies\Ex2.xml -OutputFilePath C:\WDAC\Policies\Ex7.xml -Rules $rule
Set-CIPolicyIdInfo C:\WDAC\Policies\Ex7.xml -PolicyName "Ex7 Path Rule" -ResetPolicyID
Deploy-Wdac C:\WDAC\Policies\Ex7.xml

Test: copy a tool into the folder: it runs. The same tool in C:\Temp: blocked.

Path rules are only as safe as the folder permissions. WDAC refuses path rules for folders that standard users can write to (unless option 18 is set). Keep C:\ApprovedTools writable by administrators only.

Example 8: Extend a base policy with a supplemental policy Supplemental

Define: the app team adds its own allow rules without touching the security baseline.

$base = "C:\WDAC\Policies\Ex2.xml"        # must include option 17 (Allow supplemental)
Set-RuleOption $base -Option 17
Deploy-Wdac $base

$sup = "C:\WDAC\Policies\Ex8-Sup.xml"
$d = Get-SystemDriver -ScanPath "C:\Program Files\Fabrikam" -UserPEs
New-CIPolicy -FilePath $sup -DriverFiles $d -Level FilePublisher -Fallback Hash -MultiplePolicyFormat
Set-CIPolicyIdInfo $sup -BasePolicyToSupplementPath $base -PolicyName "Ex8 Fabrikam Supplemental" -ResetPolicyID
Deploy-Wdac $sup

Test: CiTool.exe --list-policies shows a base and a supplemental. The Fabrikam app runs.

Example 9: Learn from audit, then switch to enforce Workflow

Define: the real-world recipe: audit → review → merge → enforce.

$base = "C:\WDAC\Policies\MyBase.xml"      # built in section 5, currently audit
# 1. After a few days of audit, build rules from the 3076 events
New-CIPolicy -FilePath C:\WDAC\Policies\Learned.xml -Audit -Level FilePublisher -Fallback Hash -UserPEs -MultiplePolicyFormat
# 2. REVIEW Learned.xml by hand, delete anything suspicious
Merge-CIPolicy -PolicyPaths $base, C:\WDAC\Policies\Learned.xml -OutputFilePath $base
# 3. Enforce
Set-RuleOption $base -Option 3 -Delete
Deploy-Wdac $base

Test: a program that never ran during the audit window is now blocked and logs event 3077.

Example 10: Inspect, troubleshoot and remove a policy Operate

Define: every admin needs to see what is deployed and undo it quickly.

# What is active?
CiTool.exe --list-policies

# Why was something blocked? (3077 = blocked, 3076 = would be blocked)
Get-WinEvent -LogName Microsoft-Windows-CodeIntegrity/Operational |
  Where-Object Id -in 3076,3077 |
  Select-Object -First 5 TimeCreated, Id, @{n='File';e={$_.Properties[1].Value}}

# Remove a policy by its GUID
CiTool.exe --remove-policy "{PUT-GUID-HERE}"
Restart-Computer

Test: after removal and reboot, --list-policies no longer shows it and the blocked tool runs again.

Example 11: Two base policies at the same time Multiple

Define: keep a baseline policy and add a separate "deny list" policy. A file must pass both, so the deny list only ever removes trust.

$deny = "C:\WDAC\Policies\Ex11-Deny.xml"
Copy-Item C:\Windows\schemas\CodeIntegrity\ExamplePolicies\AllowAll.xml $deny
Set-CIPolicyIdInfo $deny -PolicyName "Ex11 Deny List" -ResetPolicyID
$r = New-CIPolicyRule -DriverFilePath C:\Windows\System32\mshta.exe -Level FileName -SpecificFileNameLevel OriginalFileName -Deny
Merge-CIPolicy -PolicyPaths $deny -OutputFilePath $deny -Rules $r
Deploy-Wdac C:\WDAC\Policies\Ex2.xml       # base 1: Microsoft only
Deploy-Wdac $deny                          # base 2: allow all except mshta
CiTool.exe --list-policies

Test: two base policies are listed. Microsoft tools run; mshta.exe is blocked by base 2; third-party unsigned tools are still blocked by base 1.

Example 12: Update an existing policy safely (new version) Update

Define: add a rule to a deployed policy and replace it in place.

$x = "C:\WDAC\Policies\Ex2.xml"
Copy-Item $x "$x.bak"                                        # keep the old copy
$r = New-CIPolicyRule -FilePathRule "C:\ApprovedTools\*"
Merge-CIPolicy -PolicyPaths $x -OutputFilePath $x -Rules $r
Set-CIPolicyVersion -FilePath $x -Version "1.0.0.1"
Deploy-Wdac $x                                               # same GUID, so it replaces the old one
([xml](Get-Content $x)).SiPolicy.VersionEx

Test: a tool in C:\ApprovedTools now runs. CiTool --list-policies shows the new version number.

Example 13: Emergency rollback to audit mode Rollback

Define: enforcement broke something. Stop blocking immediately but keep logging.

$x = "C:\WDAC\Policies\Ex2.xml"
Set-RuleOption $x -Option 3                                  # audit mode ON
Set-CIPolicyVersion -FilePath $x -Version "1.0.0.2"
Deploy-Wdac $x

Test: the blocked app starts and event 3076 (not 3077) is logged. Fix the rules, then go back to enforce with Set-RuleOption $x -Option 3 -Delete.

If you cannot log in at all, boot to the recovery environment and delete the policy file: del C:\Windows\System32\CodeIntegrity\CiPolicies\Active\{GUID}.cip. This works for unsigned policies.

Example 14: Deploy the same policy to several servers Remote

Define: roll one compiled policy out to a list of Core servers.

$cip = Get-Item C:\WDAC\Binary\{GUID}.cip
$servers = "CORE01","CORE02","CORE03"
foreach ($s in $servers) {
  Copy-Item $cip "\\$s\C$\Windows\System32\CodeIntegrity\CiPolicies\Active\"
  Invoke-Command -ComputerName $s -ScriptBlock { CiTool.exe --refresh }
}
# Verify
Invoke-Command -ComputerName $servers -ScriptBlock { CiTool.exe --list-policies } | Select-String "Policy ID|Friendly"

Test: every server lists the policy. Deploy to one pilot server first, then the rest.

Example 15: Audit report of everything that would be blocked Report

Define: export the audit events to a CSV so you can review them in Excel before building rules.

Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-CodeIntegrity/Operational'; Id=3076} |
  ForEach-Object {
    [pscustomobject]@{
      Time    = $_.TimeCreated
      File    = $_.Properties[1].Value
      Process = $_.Properties[3].Value
    }
  } | Sort-Object File -Unique | Export-Csv C:\WDAC\audit-report.csv -NoTypeInformation
Import-Csv C:\WDAC\audit-report.csv | Select-Object -First 10

Test: the CSV lists each distinct file once. Approve the ones you trust and build rules for them; investigate the rest.

Property positions can differ between builds. If columns look wrong, run $e = Get-WinEvent ... -MaxEvents 1; $e.Properties | ForEach-Object Value to see the order.

Example 16: Allow the AWS Systems Manager (SSM) Agent Supplemental

Define: the SSM Agent is third-party software (Amazon), so a "Microsoft only" base policy blocks it. Instead of editing the base, add a supplemental policy that trusts the agent by its signature. Rules are built from the files that are actually installed, so no names are guessed.

Step 1: Look at what is installed and who signed it.

Get-Service AmazonSSMAgent | Format-List Name, Status, StartType
Get-ChildItem "C:\Program Files\Amazon\SSM" -Filter *.exe | ForEach-Object {
  $s = Get-AuthenticodeSignature $_.FullName
  [pscustomobject]@{ File=$_.Name; Status=$s.Status; Signer=$s.SignerCertificate.Subject }
} | Format-Table -AutoSize

Every file should show Status = Valid and the same Amazon signer. If a file is NotSigned, the Publisher rule will not cover it and the -Fallback Hash below will.

Step 2: Make sure the base policy accepts supplementals.

$base = "C:\WDAC\Policies\Ex2.xml"
Set-RuleOption $base -Option 17          # Allow supplemental policies
Deploy-Wdac $base

Step 3: Build the supplemental policy from the agent folder.

$sup = "C:\WDAC\Policies\Ex16-SSM.xml"
New-CIPolicy -FilePath $sup -ScanPath "C:\Program Files\Amazon\SSM" -Level Publisher -Fallback Hash -UserPEs -MultiplePolicyFormat
Set-CIPolicyIdInfo $sup -BasePolicyToSupplementPath $base -PolicyName "Ex16 AWS SSM Agent" -ResetPolicyID
Set-RuleOption $sup -Option 3            # start in AUDIT mode
Deploy-Wdac $sup

-Level Publisher trusts any file signed by that Amazon certificate, so agent upgrades keep working. -Fallback Hash adds exact-file rules for anything unsigned. Open Ex16-SSM.xml and check the Signers section shows an Amazon signer and nothing unexpected.

Step 4: Test in audit, then enforce.

Restart-Service AmazonSSMAgent
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-CodeIntegrity/Operational'; Id=3076,3077} -MaxEvents 20 |
  Where-Object Message -match 'Amazon|SSM' | Format-List TimeCreated, Id, Message

# No SSM events? Switch to enforce and redeploy
Set-RuleOption $sup -Option 3 -Delete
Set-CIPolicyVersion -FilePath $sup -Version "1.0.0.1"
Deploy-Wdac $sup
Restart-Service AmazonSSMAgent
Get-Service AmazonSSMAgent

Test: the service stays Running, the instance still shows Online in Systems Manager → Fleet Manager, and CiTool --list-policies shows the base plus the supplemental policy.

Run Command scripts may still fail. The agent starts PowerShell for documents such as AWS-RunPowerShellScript. Under an enforced policy, scripts that are not trusted run in Constrained Language Mode, and the agent writes them to a temporary folder under C:\ProgramData\Amazon\SSM, which you should not allow by path. Either sign your scripts and trust that signer, or keep audit mode until you know which documents you use.
Allowing the agent does not allow the apps it launches. If you use Run Command or Patch Manager, run them once in audit mode and review the 3076 events for extra files. Add other AWS software the same way, for example C:\Program Files\Amazon\EC2Launch or C:\Program Files\Amazon\AWSCLIV2, by adding a second -ScanPath run and merging with Merge-CIPolicy.

Example 17: Allow only Amazon-signed applications (plus Windows) Enforce

Define: one base policy where the only third-party trust is the Amazon publisher signature. Windows itself must stay allowed or the server will not run, so the starting point is DefaultWindows, not an empty policy. Unsigned files and other vendors are blocked, and there is no hash fallback, so an unsigned file in the Amazon folder is not trusted either.

Step 1: List every Amazon signer actually installed.

$paths = "C:\Program Files\Amazon"        # add other Amazon folders you use
Get-ChildItem $paths -Recurse -Include *.exe,*.dll -ErrorAction SilentlyContinue | ForEach-Object {
  $s = Get-AuthenticodeSignature $_.FullName
  [pscustomobject]@{ File=$_.FullName; Status=$s.Status; Signer=$s.SignerCertificate.Subject }
} | Group-Object Status, Signer | Select-Object Count, Name | Format-Table -Wrap

Expect Valid with an Amazon subject. Anything NotSigned will be blocked by this policy. Note any different Amazon subject names, since each is a separate signer.

Step 2: Start from the Windows baseline (audit).

$x = "C:\WDAC\Policies\Ex17-AmazonOnly.xml"
Copy-Item C:\Windows\schemas\CodeIntegrity\ExamplePolicies\DefaultWindows_Audit.xml $x
Set-CIPolicyIdInfo $x -PolicyName "Ex17 Windows + Amazon Only" -ResetPolicyID

Step 3: Create a publisher rule for the Amazon files and merge it.

$d    = Get-SystemDriver -ScanPath "C:\Program Files\Amazon" -UserPEs
$rule = New-CIPolicyRule -DriverFiles $d -Level Publisher      # signed files only, no hash fallback
Merge-CIPolicy -PolicyPaths $x -OutputFilePath $x -Rules $rule

Publisher = the issuing CA plus the Amazon subject name. Upgrades of the agent keep working. For tighter control use -Level FilePublisher, which also pins file name and a minimum version.

Step 4: Check that the XML contains only what you intend.

$p = [xml](Get-Content $x)
$p.SiPolicy.Rules.Rule.Option                                  # should include Enabled:Audit Mode
$p.SiPolicy.Signers.Signer | Select-Object Name                # Microsoft/Windows signers + your Amazon signer

Step 5: Deploy in audit and review.

Deploy-Wdac $x
Restart-Service AmazonSSMAgent
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-CodeIntegrity/Operational'; Id=3076} -MaxEvents 50 |
  Select-Object TimeCreated, Message | Format-List

Run for several days. Events for Amazon files mean a signer or file was missed (go back to step 1). Events for other software show what enforcement will stop.

Step 6: Enforce.

Set-RuleOption $x -Option 3 -Delete
Set-CIPolicyVersion -FilePath $x -Version "1.0.0.1"
Deploy-Wdac $x
CiTool.exe --list-policies

Test:

Get-Service AmazonSSMAgent                                      # still Running
Copy-Item C:\Windows\System32\whoami.exe C:\Temp\ -ErrorAction SilentlyContinue   # Windows binary: runs
# Run any unsigned or non-Amazon third-party .exe from C:\Temp: it must be blocked (event 3077)
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-CodeIntegrity/Operational'; Id=3077} -MaxEvents 5 | Format-List TimeCreated, Message

Rollback: set option 3 again (Set-RuleOption $x -Option 3), bump the version and redeploy, or CiTool.exe --remove-policy "{GUID}".

Check before enforcing:
  • Other Microsoft software (SQL Server, Exchange, agents) is not in DefaultWindows. Use AllowMicrosoft.xml as the starting template instead if you need it.
  • Run Command scripts still run in Constrained Language Mode unless signed (see Example 16).
  • Keep a VM checkpoint or console access until the server has been rebooted once under the enforced policy.

8. Troubleshooting and cheat sheet

Common problems

SymptomLikely cause / fix
Everything blocked after enforcingBase template missing Windows or Microsoft rules, or you skipped the audit phase. Remove the policy from a console/VM and rebuild.
Policy does not show in --list-policiesBinary file not named {PolicyID}.cip, or XML was not built with -MultiplePolicyFormat.
Supplemental policy not appliedBase lacks option 17, or BasePolicyID does not match the base.

PowerShell scripts fail with "language mode" errorsConstrained Language Mode is applied because the script is not trusted. Sign or hash-allow the script.

Best-practice checklist

  • Test in a VM with a checkpoint.
  • Always start in audit, review events, then enforce.
  • Prefer FilePublisher + Hash fallback; avoid broad Root/PCA rules for third parties.
  • Avoid path rules unless the folder is admin-only.
  • Use a base policy for the baseline and supplementals for extras.
  • Keep every XML under version control and document why each rule exists.
  • Patch cycles: re-audit after major updates.
