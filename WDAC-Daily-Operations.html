WDAC in Production: Daily Runbook

What to check every day, why it matters, and exactly how to do it.

How to use this page. Each task has the same layout: Why, Time, Steps and a script you can copy. Scripts are written for Windows Server 2025 (it has CiTool.exe) and are run from an admin PowerShell on a management server.
Test first. Try every script in your lab before using it in production. Change the paths (C:\WDAC\...) and server names to match your environment.

Policy health check

High
WhyIf a policy is missing or switched to audit, servers are no longer protected.
Time5 minutes
Good resultEvery server shows the same policies, same version, enforced.

Steps

  1. Keep a list of production servers in C:\WDAC\servers.txt (one name per line).
  2. Run the script below. It asks each server which policies are loaded and if they are enforced.
  3. Look for any line where Status is not OK.
  4. For any problem: check if a change was planned. If not, open an incident and re-deploy the approved policy (see Task 5).
PowerShell
# Expected values - change to match your environment
$ExpectedPolicy  = "Corp-Server-Base"
$ExpectedVersion = "10.0.0.5"
$servers = Get-Content C:\WDAC\servers.txt

$result = Invoke-Command -ComputerName $servers -ErrorAction SilentlyContinue -ScriptBlock {
    $dg  = Get-CimInstance Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard
    $pol = (CiTool.exe -lp -json | ConvertFrom-Json).Policies | Where-Object { -not $_.IsSystemPolicy }
    [pscustomobject]@{
        Server     = $env:COMPUTERNAME
        UserMode   = $dg.UsermodeCodeIntegrityPolicyEnforcementStatus   # 0 Off, 1 Audit, 2 Enforced
        KernelMode = $dg.CodeIntegrityPolicyEnforcementStatus
        Policies   = ($pol | ForEach-Object { "$($_.FriendlyName)|$($_.VersionString)|Enforced=$($_.IsEnforced)" }) -join '; '
    }
}

$result | ForEach-Object {
    $ok = ($_.UserMode -eq 2) -and ($_.Policies -like "*$ExpectedPolicy|$ExpectedVersion|Enforced=True*")
    $_ | Add-Member Status ($(if ($ok) {'OK'} else {'CHECK'})) -PassThru
} | Sort-Object Status | Format-Table Server, Status, UserMode, KernelMode, Policies -AutoSize

# Servers that did not answer at all
$servers | Where-Object { $_ -notin $result.Server } | ForEach-Object { "NO ANSWER: $_" }
You seeMeaningWhat to do
UserMode = 2Enforced – goodNothing
UserMode = 1Audit only – nothing is blockedWas this planned? If not, re-deploy the enforced policy.
UserMode = 0No user-mode policyServer is unprotected. Deploy policy today.
Wrong versionOld policy or failed updateRe-deploy the current version.
NO ANSWERServer offline or WinRM blockedCheck with the server team.
Note. Field names such as VersionString come from CiTool -lp -json. Run it once on your server to confirm the names on your build.

Review blocked files

High
WhyA block is either an attack stopped, or a business app broken. You must know which.
Time15 minutes
Events3077 (apps, drivers) · 8029 (scripts, MSI)

Steps

  1. Collect yesterday's block events from all servers (script below).
  2. Group them by file. The same file blocked many times is usually one issue.
  3. For each file, follow the decision chart.
  4. Write down what you decided (ticket number, allowed / escalated / ignored).
PowerShell
$servers = Get-Content C:\WDAC\servers.txt
$since   = (Get-Date).AddDays(-1)

$blocks = Invoke-Command -ComputerName $servers -ErrorAction SilentlyContinue -ScriptBlock {
    param($since)
    $logs = @(
        @{LogName='Microsoft-Windows-CodeIntegrity/Operational'; Id=3077; StartTime=$since},
        @{LogName='Microsoft-Windows-AppLocker/MSI and Script';  Id=8029; StartTime=$since}
    )
    foreach ($f in $logs) {
        Get-WinEvent -FilterHashtable $f -ErrorAction SilentlyContinue | ForEach-Object {
            # Turn the event data into simple name/value pairs
            $d = @{}
            ([xml]$_.ToXml()).Event.EventData.Data | ForEach-Object { $d[$_.Name] = $_.'#text' }
            [pscustomobject]@{
                Server  = $env:COMPUTERNAME
                Time    = $_.TimeCreated
                EventId = $_.Id
                File    = $d['File Name'] + $d['FilePath']
                Process = $d['Process Name']
                Policy  = $d['PolicyName']
                SHA256  = $d['SHA256 Hash'] + $d['Sha256Hash']
            }
        }
    }
} -ArgumentList $since

# One line per file, with how many times and on how many servers
$blocks | Group-Object File | Sort-Object Count -Descending | ForEach-Object {
    [pscustomobject]@{
        File    = $_.Name
        Times   = $_.Count
        Servers = ($_.Group.Server | Sort-Object -Unique) -join ', '
        Process = ($_.Group.Process | Select-Object -First 1)
    }
} | Format-Table -AutoSize -Wrap

$blocks | Export-Csv "C:\WDAC\Reports\Blocks_$(Get-Date -f yyyyMMdd).csv" -NoTypeInformation
Event field names. The names inside the event (File Name, Process Name, PolicyName …) can differ slightly between event types. If a column is empty, open one event in Event Viewer → Details → XML View and use the names you see there.

Review audit events (test & pilot servers)

Medium
WhyAudit mode shows what would be blocked. Fix it before you enforce.
Time10 minutes
Events3076 (apps, drivers) · 8028 (scripts, MSI)

Steps

  1. Run the Task 2 script on your pilot server list, but change the IDs to 3076 and 8028.
  2. Mark each file: needed (make a rule) or not needed (leave it blocked).
  3. For needed files, build rules straight from the audit log (below) and add them in a supplemental policy.
  4. When a pilot server shows zero new audit events for a full business cycle (often 2–4 weeks), it is ready to enforce.
PowerShell – run on the pilot server
# Build allow rules from this server's audit events
New-CIPolicy -Audit -FilePath C:\WDAC\Work\FromAudit.xml `
             -Level FilePublisher -Fallback Hash -UserPEs -MultiplePolicyFormat

# ALWAYS read the result before using it - remove anything you do not want to allow
([xml](Get-Content C:\WDAC\Work\FromAudit.xml)).SiPolicy.FileRules.ChildNodes |
    Select-Object Name, FriendlyName, FileName | Format-Table -AutoSize
Careful. -Audit turns everything that ran into an allow rule – including malware if it ran in audit mode. Review every line.

Handle requests to allow new apps

Medium
WhyBusiness needs new tools. Allow them safely, with a record.
Time15–30 min per request
RuleNo ticket, no change.

Steps

  1. Check the request. It must have: app name, version, vendor, business owner, servers, and approval from the owner's manager.
  2. Check the file. Is it signed by the real vendor? Is it clean in Microsoft Defender?
  3. Make the rule in a supplemental policy – never edit the main (base) policy for one app.
  4. Test on one pilot server. Ask the owner to confirm the app works.
  5. Deploy to the requested servers, save the XML in your repository, close the ticket.
PowerShell – check the file
$file = "D:\Install\VendorApp\app.exe"
Get-AuthenticodeSignature $file | Select-Object Status, @{n='Signer';e={$_.SignerCertificate.Subject}}
Get-FileHash $file -Algorithm SHA256
Start-MpScan -ScanType CustomScan -ScanPath $file          # Microsoft Defender scan
PowerShell – create & deploy the supplemental policy
$app      = "VendorApp"
$base     = "C:\WDAC\Repo\Corp-Server-Base.xml"            # your approved base policy
$supp     = "C:\WDAC\Repo\Supp-$app.xml"
$baseId   = ([xml](Get-Content $base)).SiPolicy.BasePolicyID

# 1. Scan the installed app folder and create rules (publisher first, hash if unsigned)
New-CIPolicy -FilePath $supp -ScanPath "C:\Program Files\VendorApp" `
             -Level FilePublisher -Fallback Hash -UserPEs -MultiplePolicyFormat

# 2. Turn it into a supplemental policy for the base
Set-CIPolicyIdInfo -FilePath $supp -SupplementsBasePolicyID $baseId -PolicyName "Supp-$app-TICKET1234" -ResetPolicyID

# 3. Compile to binary
$id = ([xml](Get-Content $supp)).SiPolicy.PolicyID
ConvertFrom-CIPolicy -XmlFilePath $supp -BinaryFilePath "C:\WDAC\Out\$id.cip"

# 4. Deploy to ONE pilot server first
$s = New-PSSession -ComputerName PILOT-SRV01
Copy-Item "C:\WDAC\Out\$id.cip" -Destination "C:\Windows\Temp\" -ToSession $s
Invoke-Command -Session $s -ScriptBlock { param($id) CiTool.exe --update-policy "C:\Windows\Temp\$id.cip" } -ArgumentList $id
Remove-PSSession $s
Good habit. Put the ticket number in the policy name. Months later you will know why each rule exists.

Detect unapproved policy changes

High
WhyAn attacker or a mistake can replace or delete a policy file.
Time5 minutes
Good resultEvery .cip file on every server matches the approved list.

Steps

  1. After every approved deployment, update the baseline file: C:\WDAC\baseline.csv (file name + SHA256 hash).
  2. Each day, compare each server's policy files to the baseline (script below).
  3. Any EXTRA, MISSING or CHANGED file = investigate. Check change tickets first.
  4. If no ticket explains it, treat it as a security incident (Task 8) and restore the approved policy from backup.
PowerShell – create the baseline (after an approved change)
Get-ChildItem C:\WDAC\Out\Approved\*.cip | Get-FileHash -Algorithm SHA256 |
    Select-Object @{n='Name';e={Split-Path $_.Path -Leaf}}, Hash |
    Export-Csv C:\WDAC\baseline.csv -NoTypeInformation
PowerShell – daily compare
$baseline = Import-Csv C:\WDAC\baseline.csv
$servers  = Get-Content C:\WDAC\servers.txt

$live = Invoke-Command -ComputerName $servers -ErrorAction SilentlyContinue -ScriptBlock {
    Get-ChildItem "$env:windir\System32\CodeIntegrity\CiPolicies\Active\*.cip" |
        Get-FileHash -Algorithm SHA256 |
        Select-Object @{n='Server';e={$env:COMPUTERNAME}}, @{n='Name';e={Split-Path $_.Path -Leaf}}, Hash
}

foreach ($srv in ($live.Server | Sort-Object -Unique)) {
    $mine = $live | Where-Object Server -eq $srv
    foreach ($b in $baseline) {
        $m = $mine | Where-Object Name -eq $b.Name
        if (-not $m)                { "$srv  MISSING  $($b.Name)" }
        elseif ($m.Hash -ne $b.Hash){ "$srv  CHANGED  $($b.Name)" }
    }
    $mine | Where-Object { $_.Name -notin $baseline.Name } | ForEach-Object { "$srv  EXTRA    $($_.Name)" }
}
Note. Windows itself may place system policies in the Active folder. Add those to the baseline once you have confirmed they are from Microsoft.

Find servers with no policy

High
WhyNew servers are often built without WDAC. They are your weakest point.
Time5 minutes
Good resultEvery server in Active Directory is in servers.txt and protected.

Steps

  1. Get all enabled Windows Server computers from Active Directory.
  2. Compare with your servers.txt list.
  3. For each new server: confirm owner, add it to the list, deploy the audit policy first, then follow the normal path to enforce.
PowerShell
Import-Module ActiveDirectory
$inAD   = Get-ADComputer -Filter 'OperatingSystem -like "*Server*" -and Enabled -eq $true' -Properties OperatingSystem, whenCreated |
          Select-Object Name, OperatingSystem, whenCreated
$inList = Get-Content C:\WDAC\servers.txt

# Servers in AD but not managed by WDAC yet
$inAD | Where-Object { $_.Name -notin $inList } | Sort-Object whenCreated -Descending | Format-Table -AutoSize

# Servers in the list but gone from AD (clean up the list)
$inList | Where-Object { $_ -notin $inAD.Name }
Fix the cause. Add the WDAC policy to your server build image or build script so new servers are protected from day one.

Confirm the backup ran

Medium
WhyIf something breaks, you need the last good policy within minutes.
Time2 minutes
Good resultBackup task result = 0, and a new backup folder from last night.

Steps

  1. Check the scheduled backup task result.
  2. Check the newest backup folder date and that it contains .cip and .xml files.
  3. If it failed, run it by hand now and find the cause (disk full, permissions, share offline).
PowerShell
Get-ScheduledTask -TaskName "WDAC-Backup" | Get-ScheduledTaskInfo |
    Select-Object LastRunTime, LastTaskResult, NextRunTime        # LastTaskResult 0 = success

$last = Get-ChildItem D:\WDAC-Backups -Directory | Sort-Object LastWriteTime -Descending | Select-Object -First 1
"Newest backup: $($last.Name)  ($($last.LastWriteTime))"
"Policy files:  " + (Get-ChildItem $last.FullName -Recurse -Include *.cip, *.xml).Count

# Also check the source repository is up to date
git -C C:\WDAC\Repo status --short
The full backup script is in the companion guide WDAC-Policy-Guide.html → section 5.

Escalate suspicious blocks

High
WhyWDAC stopped it, but the attacker may still be on the server.
TimeAs needed
OwnerYou collect facts → Security team (SOC) investigates.

Warning signs

  • File runs from Temp, Downloads, AppData, ProgramData or C:\Users\Public.
  • Started by powershell.exe, cmd.exe, wscript.exe, mshta.exe, rundll32.exe or an Office app.
  • Same unknown file blocked on many servers in a short time.
  • Unsigned file with a name that copies a Windows file (e.g. svch0st.exe).
  • Blocked driver (kernel) – often a "bring your own vulnerable driver" attack.

Steps

  1. Do not allow the file. Do not delete it either – it is evidence.
  2. Collect facts (script below): server, time, file path, hash, parent process, user.
  3. Check the hash in Microsoft Defender / your threat intel tool.
  4. Open a security incident and send the facts to the SOC.
  5. Follow the SOC's instructions (isolate server, reset passwords, etc.).
PowerShell – evidence pack
$server = "APP-SRV07"
$file   = "C:\Users\Public\update.exe"
$out    = "C:\WDAC\Incidents\$server`_$(Get-Date -f yyyyMMdd_HHmm)"
New-Item -ItemType Directory $out -Force | Out-Null

Invoke-Command -ComputerName $server -ScriptBlock {
    param($file)
    [pscustomobject]@{
        Hash      = (Get-FileHash $file -Algorithm SHA256 -ErrorAction SilentlyContinue).Hash
        Signature = (Get-AuthenticodeSignature $file -ErrorAction SilentlyContinue).Status
        Created   = (Get-Item $file -ErrorAction SilentlyContinue).CreationTime
        Events    = Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-CodeIntegrity/Operational'; Id=3077} -MaxEvents 200 |
                    Where-Object Message -like "*$(Split-Path $file -Leaf)*" | Select-Object TimeCreated, Message
        LoggedOn  = (quser 2>$null)
    }
} -ArgumentList $file | ConvertTo-Json -Depth 4 | Out-File "$out\evidence.json"
"Evidence saved to $out"

Time5 minutes (automated)

Simple report template

Run the daily checks automatically

  1. Save the scripts from Tasks 1, 2, 5, 6 and 7 as files in C:\WDAC\Scripts\.
  2. Create one "morning" script that runs them and saves the output to a dated report file.
  3. Schedule it for 06:00 on the management server, using a group Managed Service Account (gMSA) or a dedicated service account – not your own account.
  4. Each morning, open the report, act on problems, and send the summary.
PowerShell – C:\WDAC\Scripts\Morning.ps1
$day    = Get-Date -Format yyyyMMdd
$report = "C:\WDAC\Reports\Daily_$day.txt"

"WDAC Daily Report - $(Get-Date -Format 'dd MMM yyyy')" | Out-File $report
foreach ($s in "1-Health","2-Blocks","5-Drift","6-NewServers","7-Backup") {
    "`n===== $s =====" | Out-File $report -Append
    try   { & "C:\WDAC\Scripts\$s.ps1" *>&1 | Out-String -Width 250 | Out-File $report -Append }
    catch { "FAILED: $($_.Exception.Message)" | Out-File $report -Append }
}
"Report saved: $report"
PowerShell – schedule it (run once)
$action  = New-ScheduledTaskAction -Execute "powershell.exe" `
           -Argument "-NoProfile -ExecutionPolicy Bypass -File C:\WDAC\Scripts\Morning.ps1"
$trigger = New-ScheduledTaskTrigger -Daily -At 6:00AM
$princ   = New-ScheduledTaskPrincipal -UserId "CORP\gmsa-wdac$" -LogonType Password   # gMSA
Register-ScheduledTask -TaskName "WDAC-Morning-Check" -Action $action -Trigger $trigger -Principal $princ
Script rules. If PowerShell script enforcement is on (it should be), your own scripts must be signed or allowed by the policy to run in Full Language mode. Sign them with your code-signing certificate: Set-AuthenticodeSignature -FilePath .\Morning.ps1 -Certificate $cert.

Best practices for managing WDAC

Short rules that keep production safe and the work simple.

1. Audit before you enforce

Run new policies in audit mode for 2–4 weeks. Enforce only when the audit log is clean.

2. One base, many supplementals

Keep the base policy small and stable. Put each app or team in its own supplemental policy.

3. Prefer publisher rules

Use FilePublisher rules. Use hash only for unsigned files. Avoid path rules on folders users can write to.

4. Deploy in rings

Lab → pilot servers → less critical servers → critical servers. Wait at least 1–2 days between rings.

5. Always raise the version

Every change gets a higher VersionEx number. Otherwise the update is ignored.

6. Keep XML in source control

Store all policy XML in Git. Every change has a commit, a ticket number and a reviewer.

7. No ticket, no change

Every allow rule needs a business owner and an approved request. Put the ticket number in the policy name.

8. Back up every night

Back up XML, .cip files and the signing certificate (if used). Test restores every quarter.

9. Have a rollback plan ready

Keep a tested "audit" version of each policy ready to deploy within minutes.

10. Block known-bad tools

Add Microsoft's vulnerable-driver blocklist and recommended block rules to the base policy.

11. Send events to your SIEM

Forward events 3076, 3077, 8028, 8029 and 3099 to your SIEM or Microsoft Defender so the SOC can see them.

12. Protect from day one

Include WDAC in the server build process so new servers are never unprotected.

13. Sign policies when mature

Signed policies cannot be removed by an admin – stronger, but harder to roll back. Sign only after the policy is stable.

14. Limit who can change policies

Only a small, named group can deploy policies. Use separate admin accounts for this work.

One-time setup (do this before day one)

  1. Create folders on the management server: C:\WDAC\Repo, Out, Work, Reports, Scripts, Incidents.
  2. Create C:\WDAC\servers.txt (production) and C:\WDAC\pilot.txt (pilot servers).
  3. Make sure PowerShell Remoting (WinRM) works from the management server to all servers: Test-WSMan SERVER01.
  4. Put your current policy XML files into Git: git init C:\WDAC\Repo.
  5. Create the baseline file for Task 5.
  6. Schedule the nightly backup (WDAC-Backup) and the morning check (WDAC-Morning-Check).
  7. Increase the CodeIntegrity event log size on all servers (Task 10).
  8. Agree on the allow-request form and approval process with the business.
  9. Write down the emergency rollback steps and print them – you may need them when systems are down.
PowerShell
"Repo","Out","Out\Approved","Work","Reports","Scripts","Incidents" |
    ForEach-Object { New-Item -ItemType Directory -Path "C:\WDAC\$_" -Force | Out-Null }

# Test remoting to every server
Get-Content C:\WDAC\servers.txt | ForEach-Object {
    [pscustomobject]@{ Server = $_; WinRM = [bool](Test-WSMan $_ -ErrorAction SilentlyContinue) }
} | Format-Table -AutoSize

Simple glossary

WordSimple meaning
WDAC / App Control for BusinessWindows feature that only lets approved programs run.
PolicyThe list of rules: what is allowed and what is blocked.
Base policyThe main policy. Sets the core rules.
Supplemental policyAn add-on policy that allows extra apps for one base policy.
Audit modeTest mode. Nothing is blocked; Windows only writes down what it would block.
Enforced modeReal mode. Unapproved programs are blocked.
.cip fileThe compiled policy that Windows actually reads.
XML fileThe readable source of the policy. You edit this, not the .cip.
CiToolBuilt-in command to list, add and remove policies (Server 2025, Windows 11).
Publisher ruleAllow by who signed the file (e.g. "Microsoft Corporation").
Hash ruleAllow one exact file. Any change to the file breaks it.
Event 3076 / 30773076 = would have blocked (audit). 3077 = blocked (enforced).
Event 8028 / 8029Same as above, for scripts and MSI installers.
Event 3099A policy was loaded.
BaselineThe approved list of policy files and their hashes.
