WDAC Intermediate Lab

Hands-on, copy-and-run steps on Windows Server 2025 Core: build a policy, add every kind of deny rule, modify rules, and recover from a bad policy. Every step says what the command does and how to check it worked.

0. How to use this lab

You will build one small policy and keep changing it. Work in order. Each step has Run, What it does and Check.

1 Setup→2 Audit policy→3 Allow own app→4 Enforce→5 Deny rules→6 Modify→7 Rollback
Use a lab VM with a checkpoint. Do not run this on a production server. A wrong enforced policy can block PowerShell, services or even boot.
Authoring after enforcement: once a policy is enforced, your admin PowerShell session runs in Constrained Language Mode, and some of the editing commands below (for example Add-Type and .NET method calls) can fail. Do the editing while the policy is in audit mode, or author the XML on a separate admin machine and copy it over. Section 7 shows how to get back to audit when you are stuck.
How this page was checked: the helper functions (Get-WdacId, Show-WdacRules, Remove-WdacRule) were run against a sample policy XML and correctly removed rules, references and empty wrappers. The two unsigned test programs compile with Add-Type. The ConfigCI and CiTool commands need a Server or Enterprise machine and were not executed here, so run the lab on your VM and report any step that behaves differently.

Prerequisites

  • Windows Server 2025 (Core is fine), elevated PowerShell.
  • The ConfigCI module and CiTool.exe (Get-Command -Module ConfigCI, Get-Command CiTool.exe).
  • A VM snapshot or checkpoint, and a way to reach the console (Hyper-V console, not only RDP).

  2. Create folders and variables.

  3. Load the helper functions. Paste once per session. 
    function Get-WdacId($Xml){ ([xml](Get-Content $Xml)).SiPolicy.PolicyID }

function Deploy-Wdac($Xml){
  $id  = Get-WdacId $Xml
  $cip = "$W\Binary\$id.cip"
  ConvertFrom-CIPolicy -XmlFilePath $Xml -BinaryFilePath $cip
  CiTool.exe --update-policy $cip
}

function Save-WdacVersion($Xml,[string]$Version){
  Copy-Item $Xml "$W\Backup\$((Get-Item $Xml).BaseName)-$(Get-Date -f yyyyMMdd-HHmmss).xml"
  Set-CIPolicyVersion -FilePath $Xml -Version $Version
}

function Show-WdacRules($Xml){
  $p = [xml](Get-Content $Xml)
  $p.SelectNodes("//*[local-name()='FileRules']/*") | ForEach-Object {
    [pscustomobject]@{ Type=$_.LocalName; ID=$_.ID; Name=$_.FriendlyName; FileName=$_.FileName; FilePath=$_.FilePath }
  }
}

function Remove-WdacRule($Xml,[string[]]$Id){
  Copy-Item $Xml "$W\Backup\$((Get-Item $Xml).BaseName)-$(Get-Date -f yyyyMMdd-HHmmss).xml"
  $p = [xml](Get-Content $Xml)
  foreach($i in $Id){
    @($p.SelectNodes("//*[@ID='$i' and (local-name()='Deny' or local-name()='Allow' or local-name()='FileAttrib')]")) |
      ForEach-Object { [void]$_.ParentNode.RemoveChild($_) }
    @($p.SelectNodes("//*[local-name()='FileRuleRef' and @RuleID='$i']")) |
      ForEach-Object { [void]$_.ParentNode.RemoveChild($_) }
  }
  foreach($t in 'FileRulesRef','DeniedSigners','AllowedSigners'){       # empty wrappers are invalid XML for WDAC
    @($p.SelectNodes("//*[local-name()='$t' and not(*)]")) | ForEach-Object { [void]$_.ParentNode.RemoveChild($_) }
  }
  $p.Save((Get-Item $Xml).FullName)
}
    What they do:
    • Deploy-Wdac: compile the XML to {PolicyID}.cip and deploy it.
    • Save-WdacVersion: back up the XML with a time stamp, then bump the policy version.
    • Show-WdacRules: list every file rule with its ID.
    • Remove-WdacRule: delete a rule and every reference to it, and clean up wrappers that would otherwise make the XML invalid.
  4. Back up whatever is already active. 
    Copy-Item C:\Windows\System32\CodeIntegrity\CiPolicies\Active\*.cip $W\Backup -ErrorAction SilentlyContinue
CiTool.exe --list-policies
    Check: you know what was active before you started. A clean lab VM usually has only the built-in system policies.

2. Create the policy (audit mode)

Goal: a base policy that allows Windows, starts in audit mode, and can accept supplemental policies later.

  1. Start from the Windows template. 
    Get-ChildItem C:\Windows\schemas\CodeIntegrity\ExamplePolicies
Copy-Item C:\Windows\schemas\CodeIntegrity\ExamplePolicies\DefaultWindows_Audit.xml $X
    What it does: DefaultWindows trusts Windows components and Store apps. Without such a base, nothing on the server would be allowed.
    TemplateTrusts
    DefaultWindows_Audit / _EnforcedWindows components, Store apps
    AllowMicrosoftAll Microsoft-signed software
    AllowAllEverything (use as a base for deny-only policies)
    DenyAllAuditNothing (audit only, for discovery)
  2. Name it and give it a unique ID. 
    Set-CIPolicyIdInfo -FilePath $X -PolicyName "Lab Policy" -ResetPolicyID
    What it does: -ResetPolicyID creates a new GUID so you never overwrite another policy.
  3. Set rule options. 
    Set-RuleOption -FilePath $X -Option 3     # Audit mode: log, do not block
Set-RuleOption -FilePath $X -Option 16    # Apply updates without a reboot
Set-RuleOption -FilePath $X -Option 17    # Allow supplemental policies
Set-RuleOption -FilePath $X -Option 0     # Also enforce user-mode code (EXE, DLL, scripts)
    Check: ([xml](Get-Content $X)).SiPolicy.Rules.Rule.Option lists Enabled:Audit Mode, Enabled:UMCI and the others. Setting an option that is already present is harmless.
    OptionNameNote
    0Enabled:UMCIEnforce user-mode code, not only drivers.
    3Enabled:Audit ModeLog instead of block. Base policies only.
    6Enabled:Unsigned System Integrity PolicyKeep it. Templates include it. Without it the policy must be signed, and a policy you cannot delete or replace is a lab-ending mistake.
    16Enabled:Update Policy No RebootAllows later updates to apply without a reboot.
    17Enabled:Allow Supplemental PoliciesRequired on a base before a supplemental can attach.
  4. Create two test programs before you enforce. These are unsigned, so WDAC has no reason to trust them. 
    Add-Type -OutputType ConsoleApplication -OutputAssembly C:\Labs\hello.exe  -TypeDefinition 'public class P{public static void Main(){System.Console.WriteLine("hello 1 running");}}'
Add-Type -OutputType ConsoleApplication -OutputAssembly C:\Labs\hello2.exe -TypeDefinition 'public class P{public static void Main(){System.Console.WriteLine("hello 2 running");}}'
C:\Labs\hello.exe
C:\Labs\hello2.exe
    What it does: compiles two tiny console programs (Add-Type uses the .NET compiler on Windows PowerShell 5.1). If Add-Type is unavailable on your build, copy any unsigned .exe twice to C:\Labs.
  5. Deploy in audit mode and look at the result. 
    Deploy-Wdac $X
CiTool.exe --list-policies
C:\Labs\hello.exe                       # still runs: audit only logs
Get-WinEvent -LogName Microsoft-Windows-CodeIntegrity/Operational -MaxEvents 30 |
  Where-Object Id -eq 3076 | Select-Object -First 3 TimeCreated, Message | Format-List
    Check: the policy is listed, the program still runs, and event 3076 ("would have been blocked") names hello.exe.

3. Allow your own app

Allow hello.exe but not hello2.exe. The file is unsigned, so a hash rule is the right tool.

$r = New-CIPolicyRule -DriverFilePath C:\Labs\hello.exe -Level Hash
Merge-CIPolicy -PolicyPaths $X -OutputFilePath $X -Rules $r
Save-WdacVersion $X "1.0.0.1"
Show-WdacRules $X | Where-Object Name -like "*hello*"
Deploy-Wdac $X
What it does: New-CIPolicyRule makes an in-memory rule from the file's hash. Merge-CIPolicy -Rules writes it into the XML. The version is bumped so the new copy replaces the old one.

Other ways to allow software

WhenCommand
Signed vendor software, survives upgrades$d = Get-SystemDriver -ScanPath "C:\Program Files\Vendor" -UserPEs

Same, but pin file name and minimum versionNew-CIPolicyRule -DriverFiles $d -Level FilePublisher
Signed where possible, hash for the restNew-CIPolicyRule -DriverFiles $d -Level Publisher -Fallback Hash
Admin-only folderNew-CIPolicyRule -FilePathRule "C:\ApprovedTools\*"
Learn from audit eventsNew-CIPolicy -Audit -FilePath learned.xml -Level FilePublisher -Fallback Hash -UserPEs -MultiplePolicyFormat

  2. Test it.

From here on, make each change in the order edit XML → bump version → deploy → test → look at events. If your session is now in Constrained Language Mode and an edit command fails, jump to the audit fallback in section 7, edit, then re-enforce.

5. Deny rules, every type

A deny rule always wins over an allow rule, in any active policy. Deny rules are built with New-CIPolicyRule ... -Deny and merged with Merge-CIPolicy -Rules.

Rule type overview

#Deny byBlocksSurvives rename?Survives file update?Use for
1File name (Original / Internal / Description / Product)Any file with that attribute, any locationYes (uses embedded metadata)YesTools you never want, e.g. a script host
2HashOne exact fileYesNo, new build = new hashA known-bad or specific file
3PublisherEverything signed by that publisherYesYesBlocking a whole vendor
4FilePublisherOne file name from one publisher, with version rangeYesPartly (versions)One vendor tool, not the rest of the vendor
5CA / Root certificateEverything chained to that CAYesYesRarely; very broad
6PathFiles under a pathNo (moving escapes it)YesQuick block of a folder, weakest type
7Packaged appAn MSIX/Store app familyYesYesDesktop Experience machines (not Core)
Do not deny things you need to recover. Never deny cmd.exe, powershell.exe, CiTool.exe, shutdown.exe or schtasks.exe in the lab. Also never deny the Microsoft publisher or root CA: it blocks Windows itself. Keep a second console open while testing deny rules.

5.1 Deny by file name (metadata)

Test target: ftp.exe (signed by Microsoft, rarely needed). We also make a renamed copy to prove the rule uses internal metadata.

Copy-Item C:\Windows\System32\ftp.exe C:\Labs\renamed.exe
C:\Labs\renamed.exe -?                    # runs before the rule

$d1 = New-CIPolicyRule -DriverFilePath C:\Windows\System32\ftp.exe -Level FileName -SpecificFileNameLevel OriginalFileName -Deny
Merge-CIPolicy -PolicyPaths $X -OutputFilePath $X -Rules $d1
Save-WdacVersion $X "1.0.0.3"
Deploy-Wdac $X

C:\Labs\renamed.exe -?                    # blocked even though renamed
ftp.exe -?                                # blocked
What it does: the rule matches the OriginalFileName stored inside the program, not the name on disk. -SpecificFileNameLevel options: OriginalFileName, InternalName, FileDescription, ProductName, PackageFamilyName, FilePath.
# Same idea with other attributes
New-CIPolicyRule -DriverFilePath C:\Windows\System32\ftp.exe -Level FileName -SpecificFileNameLevel InternalName    -Deny
New-CIPolicyRule -DriverFilePath C:\Windows\System32\ftp.exe -Level FileName -SpecificFileNameLevel FileDescription -Deny
New-CIPolicyRule -DriverFilePath C:\Windows\System32\ftp.exe -Level FileName -SpecificFileNameLevel ProductName     -Deny
A ProductName rule is broad. Many files share one product name, so you may block more than you intended.

5.2 Deny by hash

$d2 = New-CIPolicyRule -DriverFilePath C:\Labs\hello.exe -Level Hash -Deny
Merge-CIPolicy -PolicyPaths $X -OutputFilePath $X -Rules $d2
Save-WdacVersion $X "1.0.0.4"
Deploy-Wdac $X
C:\Labs\hello.exe                         # now blocked: deny beats the allow rule from section 3
Check: the same file had an allow-by-hash rule in section 3 and is now blocked. This proves deny wins. Rename or move it, still blocked. Rebuild it, it runs again (new hash).

5.3 Deny a publisher (signer)

Pick a third-party signed file on your server. Replace the path below with your own vendor file.

$f  = "C:\Program Files\Vendor\app.exe"
Get-AuthenticodeSignature $f | Format-List Status, @{n='Signer';e={$_.SignerCertificate.Subject}}   # confirm who signed it

$d3 = New-CIPolicyRule -DriverFilePath $f -Level Publisher -Deny
Merge-CIPolicy -PolicyPaths $X -OutputFilePath $X -Rules $d3
Save-WdacVersion $X "1.0.0.5"
Deploy-Wdac $X
What it does: adds a Signer and a DeniedSigner entry for the issuing CA plus the vendor's subject name. Every file from that publisher is blocked, including future versions.

5.4 Deny one file from a publisher (FilePublisher)

$d4 = New-CIPolicyRule -DriverFilePath $f -Level FilePublisher -Deny
Merge-CIPolicy -PolicyPaths $X -OutputFilePath $X -Rules $d4
Save-WdacVersion $X "1.0.0.6"
Deploy-Wdac $X
What it does: blocks only that file name from that publisher. Open the XML and check the MinimumFileVersion / MaximumFileVersion on the generated rule to see which versions are covered.

5.5 Deny a certificate authority (very broad)

New-CIPolicyRule -DriverFilePath $f -Level PcaCertificate -Deny     # everything issued under that CA
New-CIPolicyRule -DriverFilePath $f -Level RootCertificate -Deny   # everything under that root
These can block large parts of the system if the CA also signs Windows or other software you depend on. List the rule first with Show-WdacRules, test in audit mode, and do not use them for Microsoft CAs.

5.6 Deny a path

New-Item -ItemType Directory C:\Labs\Blocked -Force | Out-Null
Copy-Item C:\Windows\System32\whoami.exe C:\Labs\Blocked\whoami-copy.exe

$d6 = New-CIPolicyRule -FilePathRule "C:\Labs\Blocked\*" -Deny
Merge-CIPolicy -PolicyPaths $X -OutputFilePath $X -Rules $d6
Save-WdacVersion $X "1.0.0.7"
Deploy-Wdac $X
C:\Labs\Blocked\whoami-copy.exe           # blocked by path; whoami in System32 still runs
Path deny rules depend on the OS build supporting them. Test them in your lab first. They are the weakest type because moving the file to another folder escapes the rule.

5.7 Deny a packaged (Store/MSIX) app

# Desktop Experience only: Server Core has no Store apps
$pkg = Get-AppxPackage -Name "*SomeApp*"
$d7  = New-CIPolicyRule -Package $pkg -Deny
Merge-CIPolicy -PolicyPaths $X -OutputFilePath $X -Rules $d7

5.8 Deny several things at once

$rules = @()
foreach ($file in "C:\Windows\System32\ftp.exe","C:\Windows\System32\telnet.exe","C:\Windows\System32\mshta.exe") {
  if (-not (Test-Path $file)) { "skip (not installed): $file"; continue }   # Server Core has fewer inbox tools
  $rules += New-CIPolicyRule -DriverFilePath $file -Level FileName -SpecificFileNameLevel OriginalFileName -Deny
}
Merge-CIPolicy -PolicyPaths $X -OutputFilePath $X -Rules $rules

5.9 Deny-only policy (alternative design)

If you only want a block list on a server that already has its own policy, make a separate base policy from AllowAll. It allows everything except what you deny, and it works alongside other base policies because a file must pass all of them.

$DX = "$W\Policies\DenyList.xml"
Copy-Item C:\Windows\schemas\CodeIntegrity\ExamplePolicies\AllowAll.xml $DX
Set-CIPolicyIdInfo $DX -PolicyName "Deny List" -ResetPolicyID
$r = New-CIPolicyRule -DriverFilePath C:\Windows\System32\ftp.exe -Level FileName -SpecificFileNameLevel OriginalFileName -Deny
Merge-CIPolicy -PolicyPaths $DX -OutputFilePath $DX -Rules $r
Set-RuleOption $DX -Option 3       # audit first
Deploy-Wdac $DX

Check the result of any deny rule

Show-WdacRules $X | Where-Object Type -eq 'Deny' | Format-Table -AutoSize
$p = [xml](Get-Content $X)
$p.SiPolicy.Signers.Signer | Select-Object ID, Name                                     # all signers
$p.SiPolicy.SigningScenarios.SigningScenario.ProductSigners.DeniedSigners.DeniedSigner   # denied signers

6. Modify and remove rules

6.1 See what is in the policy

Show-WdacRules $X | Format-Table -AutoSize
(([xml](Get-Content $X)).SiPolicy.Rules.Rule.Option)

6.2 Remove a deny rule

Show-WdacRules $X | Where-Object { $_.Type -eq 'Deny' -and $_.Name -like '*hello*' }   # note the IDs
$ids = Show-WdacRules $X | Where-Object { $_.Type -eq 'Deny' -and $_.Name -like '*hello*' } | ForEach-Object ID
Remove-WdacRule $X $ids
Save-WdacVersion $X "1.0.0.8"
ConvertFrom-CIPolicy $X "$env:TEMP\dryrun.cip"    # dry-run compile outside Binary: errors mean a dangling reference
Deploy-Wdac $X
C:\Labs\hello.exe                                  # allowed again (the section 3 allow rule is still there)
What it does: removes the rule element and every FileRuleRef that points at it. If you only delete the rule and leave the reference behind, compilation fails with an error naming the element.
A typical error is "The element 'FileRulesRef' ... has incomplete content". It means a wrapper was left empty. Remove-WdacRule already cleans these up. If you edit by hand, delete the empty FileRulesRef element.

6.3 Remove a deny rule for a signer

$p = [xml](Get-Content $X)
$p.SiPolicy.Signers.Signer | Select-Object ID, Name              # find the signer ID
$sid = "ID_SIGNER_S_XXXX"
Copy-Item $X "$W\Backup\before-signer-removal.xml"
@($p.SelectNodes("//*[local-name()='DeniedSigner' and @SignerId='$sid']")) | ForEach-Object { [void]$_.ParentNode.RemoveChild($_) }
@($p.SelectNodes("//*[local-name()='DeniedSigners' and not(*)]"))         | ForEach-Object { [void]$_.ParentNode.RemoveChild($_) }
if (-not $p.SelectNodes("//*[@SignerId='$sid']").Count) {
  @($p.SelectNodes("//*[local-name()='Signer' and @ID='$sid']")) | ForEach-Object { [void]$_.ParentNode.RemoveChild($_) }
}
$p.Save((Get-Item $X).FullName)
Save-WdacVersion $X "1.0.0.9"; Deploy-Wdac $X

7. Emergency rollback

Pick the lightest fix that works. Try them in this order.

SituationAction
An app is blocked and you can still run commandsA or B
You can only run cmd and CiTool.exe (PowerShell is blocked)B (remove) from cmd
You have an older working policy fileC (restore)
You cannot sign in or the server will not start normallyD (offline delete) or the VM checkpoint
You are about to try something riskyE first (automatic rollback)

A. Flip to audit mode (best first step)

Set-RuleOption $X -Option 3
Save-WdacVersion $X "1.0.2.0"
Deploy-Wdac $X
C:\Labs\hello2.exe                        # runs again; event 3076 instead of 3077
Why it works: same policy and same GUID, only the mode changes. Nothing is blocked but everything is still logged, so you can see what to fix.

B. Remove the policy

CiTool.exe --list-policies                      # find the PolicyID
$id = Get-WdacId $X
CiTool.exe --remove-policy $id
# from cmd.exe if PowerShell is blocked:
# CiTool.exe --remove-policy {GUID}
Restart-Computer                                 # if the policy is still listed afterwards

C. Restore a known-good copy

Get-ChildItem $W\Backup | Sort-Object LastWriteTime -Descending | Select-Object -First 5 Name
Copy-Item $W\Backup\LabPolicy-XXXX.xml $X -Force      # pick a good version
Set-CIPolicyVersion -FilePath $X -Version "1.0.3.0"   # bump above the broken one
Deploy-Wdac $X
Always bump the version when you redeploy an older XML. A same-or-lower version can be confusing to track and can be refused for signed policies.

D. Offline delete (locked out)

  1. Restore the VM checkpoint if you have one. This is the fastest.
  2. Or boot to the Windows Recovery Environment / Server install media → Repair → Command Prompt.
  3. Find the Windows drive letter (it is often not C: in WinRE) and delete the bad policy file: 
    dir D:\Windows\System32\CodeIntegrity\CiPolicies\Active
del D:\Windows\System32\CodeIntegrity\CiPolicies\Active\{GUID}.cip
  4. Multiple-policy files can also be copied to the EFI system partition. If the policy still loads after a reboot, delete that copy too: 
    mountvol S: /S
dir S:\EFI\Microsoft\Boot\CiPolicies\Active
del S:\EFI\Microsoft\Boot\CiPolicies\Active\{GUID}.cip
mountvol S: /D
  5. Reboot normally.
This works for unsigned policies, which is all this lab uses. A signed policy cannot be removed this way. That is why signing is an advanced topic and should not be used while learning.

E. Dead-man switch: automatic rollback

Before any risky change, schedule a rollback that fires unless you cancel it.

$id = Get-WdacId $X
$a  = New-ScheduledTaskAction -Execute "C:\Windows\System32\CiTool.exe" -Argument "--remove-policy $id"
$t  = New-ScheduledTaskTrigger -Once -At (Get-Date).AddMinutes(20)
Register-ScheduledTask -TaskName "WDAC-Rollback" -Action $a -Trigger $t -User SYSTEM -RunLevel Highest | Out-Null

# ...apply and test your risky change...

# Happy? Cancel the rollback:
Unregister-ScheduledTask -TaskName "WDAC-Rollback" -Confirm:$false
What it does: in 20 minutes the SYSTEM account runs CiTool --remove-policy, even if your session is blocked or disconnected. To roll back to audit instead of removing, compile an audit copy of the policy first and schedule CiTool.exe --update-policy with that file.

Rollback drill (do this once)

  1. Deny hello.exe by hash (5.2) and confirm it is blocked.
  2. Run action A and confirm it runs.
  3. Set enforce again, then run action B and confirm CiTool --list-policies no longer lists your policy.
  4. Redeploy with action C from a backup.
  5. Set up action E, wait for it to fire once, then cancel it next time.

Safe-change checklist

  • Checkpoint or backup taken.
  • Change tested in audit mode first.
  • Second console session open.
  • Dead-man switch scheduled.
  • Not denying cmd, powershell, CiTool.
  • Version bumped, XML backed up.

8. Multiple policies and supplementals

SetupEffective result
One base policyThat policy decides.
Base + supplemental (needs option 17 on the base)Files allowed by base or supplemental, minus any deny.
Two base policiesA file must be allowed by both. Either one can block it.

Add a supplemental policy for another app

$S = "$W\Policies\Supp-Vendor.xml"
$base = $X
New-CIPolicy -FilePath $S -ScanPath "C:\Program Files\Vendor" -Level Publisher -Fallback Hash -UserPEs -MultiplePolicyFormat
Set-CIPolicyIdInfo $S -BasePolicyToSupplementPath $base -PolicyName "Supp Vendor" -ResetPolicyID
Deploy-Wdac $S
CiTool.exe --list-policies
Check: one base and one supplemental are listed. Deny rules in the base still apply to the supplemental's files.
A supplemental policy has no mode of its own. It follows its base, so test in audit by putting the base in audit (Set-RuleOption $X -Option 3). Do not set option 3 on the supplemental, and keep deny rules in the base policy.

Remove them in the right order

CiTool.exe --remove-policy (Get-WdacId $S)     # supplemental first
CiTool.exe --remove-policy (Get-WdacId $X)     # then the base

10. Cleanup

Get-ScheduledTask -TaskName WDAC-Rollback -ErrorAction SilentlyContinue | Unregister-ScheduledTask -Confirm:$false
Get-ChildItem $W\Binary\{*}.cip | ForEach-Object { CiTool.exe --remove-policy $_.BaseName }   # file names are the policy GUIDs
CiTool.exe --list-policies
Remove-Item C:\Labs -Recurse -Force
Restart-Computer
Check: your lab policies are gone from --list-policies after the reboot. Keep C:\WDAC\Policies and Backup for reference.
